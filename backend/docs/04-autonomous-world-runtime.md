# Autonomous World Runtime and Recovery Design

**Status:** Target architecture and implementation plan  
**Related specifications:** [01.md](./01.md), [02.md](./02.md), [03.md](./03.md)  
**Purpose:** Define what it means for SIM SOCCER to be alive, time-synchronized, recoverable, and autonomous.

## 1. The Goal

SIM SOCCER is not a collection of commands that an operator runs for each match. It is a persistent virtual football world that an operator starts once and that then manages its own seasons. Seasons are numbered virtual cycles such as `Season 1`, `Season 2`, and `Season 3`; calendar years are not required as season identity.

```text
Start runtime
  -> verify dependencies
  -> load and reconcile persisted world state
  -> prepare upcoming fixtures and markets
  -> start matches at their scheduled real-world times
  -> advance match state from elapsed time
  -> persist and broadcast events
  -> finish, settle, update tables and ratings
  -> wait the configured interval
  -> advance to the next round
  -> complete the season and prepare the next one
```

The frontend is a client of this world, not its clock or controller. A disconnected browser must not pause, restart, or alter a match. The database continues to represent the world while the API, worker, or frontend is offline.

Each world round is shared across the configured competitions. Round 1 includes every Round 1 fixture in the Premier League, La Liga, and Serie A, and all fixtures in that round share one kickoff time. One match finishing must not prevent the other fixtures from starting. The world advances to Round 2 only after every Round 1 fixture across all three competitions and its required post-match processing have completed. Then the configured ten-minute world break begins.

## 2. Decisions That Resolve the Existing Specifications

The documents describe the same goal at different levels, but one older lifecycle proposal conflicts with the newer match model:

- `01.md` section 72 describes calculating a final result and timeline before kickoff.
- `03.md` requires the result to emerge from event-by-event state transitions; the future score and event sequence must not already be decided at kickoff.
- `02.md` describes the dynamic match state, player/team evolution, and shared state that influences all event types.

**Decision:** Use `03.md`'s event-by-event model as authoritative for match execution. Keep `01.md`'s lifecycle, persistence, security, and betting requirements, but adapt any pre-generation step to prepare inputs, lineups, ratings, and markets, not a hidden final score or complete future timeline. Persist checkpoints and events as they occur.

The season controller, not the API request or browser, decides what match is next. Betting consumes the published state and must never influence the football outcome.

Fixture schedules and results are generated by this virtual world. Initial configured club data may bootstrap a competition, but runtime scheduling and results must not depend on a live football fixture/results API.

### Separate match outcomes from bet settlement

The simulation owns football state and commits the final match result. A separate settlement process consumes that committed result, finds pending selections for that specific fixture, and settles them idempotently. Do not make the match simulation itself perform betting or wallet operations. Settlement may follow a fixture's completion asynchronously; it must not block unrelated matches, while the world round must wait for required settlement work before advancing.

## 3. Sources of Truth

### PostgreSQL: durable world truth

PostgreSQL owns:

- numbered virtual seasons (`Season 1`, `Season 2`, ...), the shared world round, round schedule, and season status;
- fixture kickoff timestamps and lifecycle status;
- match seed, simulation version, elapsed virtual time, current score, and current state;
- ordered match events and snapshots/checkpoints;
- team/player ratings, standings, markets, bets, settlements, and audit records;
- runtime heartbeat, last reconciliation, and coordinator ownership/lease.

A restart reconstructs the world from these records. Important progress must not exist only in process memory.

### Redis and BullMQ: recoverable coordination

Redis transports jobs and supports worker coordination. It is not the permanent record of which season or match exists. Jobs must be safe to enqueue more than once; on restart, reconciliation compares PostgreSQL state with queue state and recreates missing work.

### UTC wall clock: world time

Use one authoritative UTC clock for scheduling and reconciliation, preferably PostgreSQL's clock for decisions shared by multiple processes. Do not advance match time by counting `setInterval` callbacks. A delayed or offline process must calculate elapsed time from persisted timestamps.

## 4. Time and Round Scheduling

Persist an explicit `scheduled_at` for every fixture. Normal runtime represents 90 virtual match minutes as 90 real minutes: `MATCH_REAL_DURATION_SECONDS` should default to `5400`. A shorter duration may be used only by isolated automated tests or an explicitly requested demonstration mode; it must not silently become the normal world clock.

```text
targetVirtualSecond = clamp(
  floor((authoritativeNow - actualKickoffAt)
        * 5400 / MATCH_REAL_DURATION_SECONDS),
  0,
  5400
)
```

Persist the actual kickoff, last processed virtual second, last event sequence, and latest checkpoint. On recovery, advance deterministically from that checkpoint to the virtual time implied by the current clock. If downtime means events are overdue, persist and broadcast them in order as catch-up events; do not skip them or reset the match to zero.

World-round scheduling is durable data, not a timer in RAM. One world round includes fixtures from all configured leagues:

1. Generate the round's fixtures internally for the Premier League, La Liga, and Serie A; do not fetch real-world fixture lists or scores.
2. Assign and persist one shared kickoff time for every fixture in a world round across the three leagues. Space round kickoffs by the match duration plus the configured world break, and ensure the first schedule gives the configured market preparation buffer.
3. Make upcoming fixtures and markets discoverable before kickoff so users can place bets; close each fixture's markets at its persisted kickoff.
4. Start each match at its scheduled time, independently of other matches and browser connections. Matches in one league must not block matches in another.
5. Mark the world round complete only after every fixture across all configured leagues has finished and required result, table, rating, and settlement work has committed.
6. Start one ten-minute world break after the final fixture in that shared round completes, then start every fixture in the next world round together. Store the schedule durably; do not maintain it only in worker memory.

Each competition maintains its own table, but all competitions share the round number, kickoff time, and round transition.

## 5. Startup and Reconciliation Contract

`npm start` launches exactly one API, one world coordinator/scheduler, and the required worker process(es) as one supervised runtime. It must not silently run migrations or seed a remote database. Schema deployment and first-time club/Season 1 initialization remain explicit, guarded operations.

Startup proceeds in these phases:

1. **Configuration:** validate required environment variables without logging credentials.
2. **Dependency preflight:** verify PostgreSQL with a read-only query and Redis with `PING`. Do not start world mutations until the world dependencies are healthy.
3. **Ownership:** acquire a database-backed lease or advisory lock for the singleton world coordinator. API and worker processes may be replicated, but only one active coordinator should schedule rounds.
4. **Load:** read the active numbered season, shared world round, all three competitions' fixtures, matches, checkpoints, pending settlements, and runtime record from PostgreSQL.
5. **Reconcile:** compare persisted state to authoritative UTC time; find overdue kickoffs, stale `LIVE` matches, missing simulation/settlement jobs, incomplete rounds, and pending next-round transitions. Apply only idempotent repairs.
6. **Run:** start the coordinator loop and workers, publish readiness, and continuously update the runtime heartbeat.

If there is no active seeded season, report `WAITING_FOR_SEASON` and remain healthy for API/admin work; do not invent a season. If PostgreSQL is unavailable, do not mutate football or betting state. If Redis is unavailable, report the world as degraded and retry/reconcile; do not claim jobs were queued.

## 6. Match Execution and Recovery

The current-state simulation follows `03.md` and advances each fixture on its own real-time clock:

```text
load checkpoint
  -> calculate hazards from current state
  -> sample the next event using the persisted deterministic stream
  -> apply event and state changes
  -> persist event, state, sequence and virtual time
  -> broadcast the committed event
  -> repeat until target virtual time or full time
```

Before a match starts, persist its immutable inputs: team/player snapshot, simulation version, seed, and match configuration. During play, persist checkpoints frequently enough that recovery is bounded. A checkpoint includes the entire dynamic match state and random-generator state, not just the score. Use unique database constraints such as `(fixture_id, sequence)` so a retry cannot insert duplicate events.

The commit-before-broadcast rule is mandatory: persist an event first, then broadcast it. Use an outbox or an equivalent replayable broadcast cursor so a crash between commit and WebSocket delivery does not lose the event. Reconnecting clients provide their last sequence and receive all later persisted events in order.

At full time, commit the fixture's final score and statistics first. A separate settlement consumer then reads the result and the pending bets linked to that fixture, settles them transactionally and idempotently, and records completion. A slow settlement for one fixture must not stall simulation of other fixtures, but it remains required world-round work.

When a worker restarts:

- `SCHEDULED` with future kickoff: leave it scheduled and ensure its job exists.
- `SCHEDULED` with elapsed kickoff: claim it idempotently and begin/reconcile it at the correct virtual time.
- `LIVE` with a checkpoint: restore it and catch up from persisted time to current time.
- `FINISHED` with missing settlement/evolution work: enqueue only the missing idempotent follow-up work.
- `FINISHED` with complete follow-up: do nothing.

Never rerun a finished match from kickoff just because a queue job is retried. Do not turn a partially persisted run into a second score or a second payout.

## 7. Live Operator Feedback

The terminal should show state transitions and periodic summaries, not just "started successfully" and not one log line per simulated second. Use structured logs with timestamps and identifiers, for example:

```text
BOOT database=connected redis=connected
WORLD status=RECOVERING season="Season 1" round=1 overdue=2
WORLD status=RUNNING season="Season 1" round=1 active=6 next_round_at=...
MATCH status=LIVE league=Premier-League home=... away=... score=1-0 minute=34 events=18
ROUND status=COMPLETE season="Season 1" round=1 next_round_at=...
WORLD status=DEGRADED dependency=redis retry_in=5s
```

Emit a heartbeat/status summary at a modest interval (for example, every 15 seconds) and on lifecycle changes. Include active season/round, live and completed fixtures, next kickoff, queue depth/failures, database/Redis health, and last reconciliation time. Do not log tokens, connection strings, or user secrets.

Expose separate endpoints:

- `/api/health/live`: the process can respond.
- `/api/health/ready`: critical dependencies are usable for the advertised service.
- `/api/world/status`: world state, last heartbeat/reconciliation, season/round, active fixtures, and degraded reason.

An API process being alive is not proof that the world coordinator is running. The status endpoint and heartbeat make that difference visible.

## 8. Current Implementation vs Target

| Capability | Current state | Target |
| --- | --- | --- |
| `npm start` | Builds, checks PostgreSQL/Redis, starts API, coordinator, and worker | Remains the single supervised world command |
| Database/Redis | Connection checks exist; health routes exist | Continuous health, readiness, heartbeat, and degraded recovery |
| Season identity | Seed supports year-labelled names; next-season code derives calendar years | Use `Season 1`, `Season 2`, ... independent of real-world years |
| Fixtures | Seed and coordinator generate virtual fixtures; coordinator loops through active competitions | Give every fixture in a shared world round the same kickoff across all configured leagues |
| Simulation | Worker persists events/checkpoints and uses UTC progression; concurrency is configurable | Normal 90 virtual minutes take 90 real minutes; concurrent matches keep pace without blocking each other |
| Recovery | Snapshot restoration and event uniqueness exist, but complete restart recovery is not proven | Restart reconciles each live fixture to UTC and resumes without duplicate events/results |
| Round progression | Coordinator advances leagues independently | Advance all three competitions together after the entire world round and required processing complete |
| Betting settlement | Match worker currently calls settlement after its simulation | Separate result consumer settles only bets linked to that fixture, idempotently |
| Markets | Coordinator prepares markets before kickoff and closes them at kickoff | Keep this behavior while preparing each upcoming world-round fixture in advance |
| Observability | Startup logs and world-status endpoint exist | Periodic shared-round heartbeat/status and actionable dependency/queue health |

The latest code includes snapshot saving/restoration and batched wall-clock progression, but a successful build or in-memory snapshot test does not prove process-restart recovery. The current code still needs the shared global-round controller, year-independent season labels, separate settlement consumer, normal 90-minute real duration, and a real end-to-end restart test. The currently running process must be restarted before worker concurrency or clock changes take effect.

## 9. Implementation Sequence

Build and verify the world in these increments:

1. **Season identity:** use persisted virtual sequence labels (`Season 1`, `Season 2`, ...). Do not infer season identity from calendar years.
2. **Shared round model:** persist one world round covering every configured league, with synchronized fixture kickoffs and a global round-completion barrier.
3. **Real-time match clock:** set the normal match duration to 5,400 real seconds for 5,400 virtual seconds; retain shortened timing only for explicit isolated tests.
4. **Checkpointed simulation:** save complete match/RNG state and event sequence; process multiple fixtures concurrently within configured database capacity; test actual restart/catch-up.
5. **Independent settlement:** commit match results, then publish/queue settlement work for a separate consumer that settles only the relevant fixture's pending selections.
6. **Round and season controller:** after all fixtures and required work for the shared round complete, wait ten minutes and run the next round. After the final round, advance to the next numbered season using virtual club data.
7. **Failure testing:** stop the API, coordinator, or worker during matches; interrupt Redis; simulate PostgreSQL loss; restart and verify no lost/duplicate events, results, table updates, or payouts.

Each phase should be deployable and observable before adding the next. Do not label the system autonomous until the final end-to-end test passes.

## 10. Definition of Done

The autonomous world is ready only when these tests pass against an isolated development environment:

- One command starts exactly one API, coordinator, and required workers after dependency checks; logs show which services became ready.
- A virtual `Season 1` runs all fixtures for Round 1 across all three competitions, with synchronized real-time kickoffs and no external fixture/result feed.
- Upcoming shared-round fixtures and markets are persisted and visible before their kickoffs without manual enqueue commands.
- Every match's 90 virtual minutes take 90 real minutes in normal runtime; test acceleration is explicit and isolated.
- Round 2 begins only after every Round 1 fixture across all three competitions and its required result/table/settlement work completes, followed by the configured ten-minute break.
- Stopping the frontend or disconnecting all clients does not pause the world.
- Stopping the runtime during any match and restarting it reconciles to current UTC time, resumes from a checkpoint, and preserves ordered events without duplicates.
- Redis loss/restart does not erase season, match, result, bet, or wallet truth; jobs are reconstructed from PostgreSQL.
- PostgreSQL loss prevents unsafe writes and produces a visible degraded state.
- Match result persistence and separate per-fixture settlement, ratings/standings, round delay, and next-round scheduling are idempotent.
- Seasons are identified as `Season 1`, `Season 2`, etc. The world completes and advances seasons without year-derived names or manual `simulate`, `settle`, or `next round` commands.
- Logs and `/api/world/status` agree with the persisted database state.

Until these are true, `npm start` means "start the currently implemented API and worker," not "run the autonomous football world."
